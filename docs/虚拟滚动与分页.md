# OneTab 不卡补丁 v2 · 虚拟滚动 + 分页

> 接续 `docs/findings.md`（诊断报告）与早期的「一行 CSS」方案（退役说明见 `docs/实测数据与工具.md`）。
> 这一份说的是最终形态：**两层虚拟滚动 + 分页**，解决官方 OneTab「条目一多，哪里都卡」的根因。

## 一句话

官方把 5206 条记录（5.6 万个 DOM 节点、5600 多个布局盒子）一次性全摆上桌，浏览器每动一下鼠标都要把整桌盘一遍。补丁做的事：**只把看得见的摆上桌，其余的收进仓库，但用占位符撑住原来的空间**——看起来一模一样，账本小了 90%。

## 实测数据（5206 条真实数据，144Hz，帧预算 6.9ms）

| 场景 | 官方原状 | 补丁后 | 说明 |
|---|---|---|---|
| 滚动时主线程占用 | 18.0% | **2.6%** | 5 秒滚动 A/B，同页对照 |
| 鼠标命中测试 p50 | 2.6 ms | **0.3 ms** | 超出帧预算就是掉帧 |
| 点击打开条目 | 0.8 ms 处理 + 整页僵住 | **0.5 ms，阻塞 0** | 无长任务 |
| 批量追加 100 条 | 3.7 ms（且全量重排风险） | **2.6 ms，阻塞 0** | 只量新增的 100 行 |
| 参与布局的行数 | 5206 | **100**（仅当前页） | 成本与总条目数解耦 |
| 打开列表页 | 官方自身渲染 ~0.7s | +1.0s（含一次性全量测量） | 见「已知边界」 |

## 两层虚拟滚动

官方结构是三层：分组 `.tabGroup` → 行容器（`.tab` 的直接父元素）→ 行 `.tab`。补丁在这两层各自做「摘除 + 补高」：

- **组层**：视口外 1400px 以外的整组 `display:none`，这是大头（一消失就是几百行）。
- **行层**：组内视口外 320px 以外的行 `display:none`。
- **补高**：被摘掉的高度用宿主容器的 `padding-top/bottom` 顶住，所以滚动条长度、滚动位置、每一行的像素位置**分毫不动**。

高度模型是一条恒等式：`容器高度 = 边框 + 基准padding + 首元素外边距 + 内容跨度 + extra`。前三项和 extra 在容器「原状」时量一次就固定不变；内容跨度 = Σ(每行高度 + 间距)，按元素用 WeakMap 缓存。于是：

- 新增 100 行 → 只量这 100 行，跨度重算，高度自动跟上；
- 滚动 / 点击 → 完全不碰测量，只做 class 增删；
- 显示永远靠「不加隐藏 class」，官方自己的搜索、折叠、筛选逻辑一概不被覆盖。

安全性：只加/去 class、写 padding，**从不删节点、不改官方结构**；连续出错 3 次自动整体回滚。

## 分页（v2 新增）

虚拟滚动解决了「摆上桌之后的卡」，但打开列表页时官方仍要先把 5.6 万个节点全部建出来。分页是数据面的釜底抽薪：

- **翻页条**在列表顶部和底部各一条：上一页 / 下一页 / 「第 x / y 页 · n 条」/ 每页 50·100·200 条下拉框。样式跟随官方字体与灰阶。
- **每页条数记忆**在 `localStorage`（键 `otvzPageSize`），下次打开保持你的选择。
- **切片只数「官方可见行」**：官方搜索或折叠藏掉的行不占页名额。所以官方自带搜索照常用——搜出 80 条就只有一页，搜出 500 条自然分成 5 页，不需要我们碰搜索的任何代码。
- **总行数退回一页以内**时（比如删掉大量条目），自动退回纯虚拟滚动模式，翻页条消失，界面和官方完全一致。
- **翻页条打开瞬间就有（先遣条）**：官方把几千条从存储读出来渲染进页面要好几秒。补丁在启动的第一毫秒就把翻页条挂进页面骨架（此时 `#contentAreaDiv` 还是官方写死的静态 HTML，必然存在），先显示「加载中…」；官方开始渲染后显示实时进度（「第 1/3 页 · 280 条」），渲染完自动变成「第 1/53 页 · 5232 条」并挪到列表容器的正式位置。实测探针里翻页条在页面加载后 **约 100 毫秒** 内出现。只有「渲染完且总数不足一页」的小数据页面才会在 5 秒后收走先遣条（数据太少本来就不需要翻页）。
- 翻页条插在列表容器的**前后兄弟位置**，不进定位模型，不碰官方 DOM 结构。

翻页后只显示当前页的 100 行：页外的整容器直接 `display:none`（子树不参与样式重算），当前页内全部真实显示。每页 ≤200 条时页内不需要再收缩视口——200 个盒子对 144Hz 来说毫无压力。

## 首屏直出（v3 新增）

前面两代解决的是「摆上桌之后」和「摆多少」；但只要官方还在从存储里读 5000 多条、建 5.6 万个节点，打开页面的头几秒屏幕上就是空的。首屏直出把这段空白也填掉：

- **翻页条出现 ≠ 有内容可看。** 打开页面后一刻，补丁就自己搭一个「官方同款壳」——包装链的内联样式（63px 顶栏让位、fixed 列容器、滚动容器、全宽列表区）都是从官方实拍 DOM 逐字抄的，宽窄、边距、滚动位置与官方一致，所以换装时不会跳。
- **直接读第一页，不等官方。** 补丁绕过官方的全量模型，直接查 IndexedDB：`root` 记录里的 `childIds` 就是显示顺序（树序即屏序），按序取到「装满一页」为止（约 180 条），用官方同款模板拼出 HTML 摆上桌。实测 **约 0.4 秒**第一页就可读可点。
- **官方在后台照常渲染。** 官方那份列容器被 `opacity:0` + `content-visibility:hidden` 按住——不绘制、不参与布局、不接点击，但**仍在渲染树里、`IntersectionObserver` 照常判相交**，所以官方自己的分片渲染继续推进，只是用户看不见也不被它的布局开销拖累（见下方「让官方渲染在复刻期停住」）。
  - 注意这里**不能**用 `visibility:hidden`：它会让 `IntersectionObserver` 判定为不可见，官方渲染会直接卡住不启动（踩过这个坑）。也不能用 `display:none`，那会让补丁测不出行高。
- **无缝换装。** 补丁第一页分页就绪后，榚被摘掉、官方容器恢复可见，其间尽量把滚动位置带过去；小数据页面在行数稳定后立即换装；12 秒兜底强制换装。
- **外观零差异**：行模板、组模板（标签、日期行、折页钮、全部还原、更多…、分割线）逐字符复刻实拍 DOM；favicon 直接沿用官方的 `images/iconGrid.webp` 雪碧图（1136 个域名的格子号从官方源码整体搬运，未收录的域名走官方同款 gstatic favicon 服务）。
- **复刻期的组头按钮显示「加载中」**：这 3–4 秒里「全部还原 / 更多… / 折页」还不能真操作——官方把它们绑在框架实例上，复刻的静态 DOM 进不去（详见下节）。与其让用户点了没反应，不如把这个状态画在脸上：这三个按钮在复刻期挂 `data-otvz-pending` 属性，被 CSS 处理成半透明灰 + 极轻的呼吸动画 + 禁用手型，同时带 `title="还在加载，稍后可用"`。**纯外观，不碰官方状态**：不做任何拦截（链接照常可点），复刻 DOM 整段摘掉时属性随之消失，官方自己的按钮一点不受影响。`@media (prefers-reduced-motion: reduce)` 下呼吸动画自动关闭。

### 为什么复刻期的组头按钮不做成可点
不是偷懒，是三个实测出来的硬冲突：

1. **官方按钮认「实例」不认 DOM。** 官方绑定是 `Q(k.i, "click", …)`——`k.i` 是框架实例自己的元素引用，点击走实例方法（如折页的 `this.rf()`）。复刻行是字符串拼出来的 `<div>`，不在官方实例树里，要让它可点只能绕官方内部路径调私有方法。
2. **「折页」官方没留公开派发口。** 官方确有一个 `clickTabGroupButton` 派发入口，但只认 `restoreAllButton / moreButton / deleteAllButton / toggleLockTabGroupButton` 四种，**没有 `foldButton`**——所以折页必然要碰最脏的内部路径。
3. **折页会踩到分页的可见性规则。** 折页真正做的事是把 `folded` 写进 IndexedDB 并折叠该组，而本补丁的分页切片规则是「按官方可见行计数」。两者撞上会导致：点了复刻画面不塌（画面是静态拼的）、1~2 秒后官方接管时突然折叠（视觉跳变），或者页边界与官方可见行对不上（某页只有十几行 / 末尾多一页空的）。
4. **复刻期官方模型还没搭完。** 复刻可见的 0.4s ~ 3.8s 之间，官方列表正在后台长出来，实例树是残缺的。「全部还原」会真去动 `chrome.windows` / 开标签页，模型半成品时触发可能只还原了已加载的那部分；「更多…」的菜单锚点是实例元素，此时可能还没建、导致菜单定位错位。

结论：为了这 3.4 秒的操作能力去冒破坏稳定分页的风险，不划算。**"加载中"外观是收益/风险比最高的做法。**

### 左侧预留：对齐官方三栏（v3.1）

官方页面是三栏 flex 布局（实测盒子模型，窗口宽 1400 / 1800 下完全一致 → 侧栏是固定宽，不随窗口变）：

| 栏 | 起点 x | 宽度 | flex | 关键样式 |
|---|---|---|---|---|
| `navCol`（侧栏） | 0 | **300** | `0 1 auto` | `margin-inline-end: -12px` |
| `centerCol`（中栏） | **288** | 余量 | `1 1 0` | `padding-inline: 10px 40px`、`min-width: 420px` |
| `quickAccessCol`（右栏） | 末尾 | 0（默认折叠） | `0 1 auto` | — |

侧栏因 `-12px` 负边距，中栏实际从 **288** 开始（不是 300）。

**问题**：这三栏是官方模型就绪后**一起**出现的；而复刻壳只画中栏。不预留的话，换装瞬间列表会从通栏（1376）被挤成 1038 并整体右移——用户看到的就是「先一屏通栏列表，过了一会儿侧栏啪一下冒出来，列表还缩了一下」。

**做法**：复刻壳在中栏前预留一个 `288px` 的空 div（`data-otvz-replica-navcol`，`aria-hidden`），底色与三栏容器一致。于是换装前后中栏位置分毫不差，跳动消失。

⚠️ **底色必须用 `var(--col-bg-color)`，不能写死 `rgb(247,248,250)`** —— 该变量亮色是 `#f7f8fa`、暗色是 `#222222`，写死会在暗色主题下露出一条亮灰带。

⚠️ 这个预留块是**纯占位**：不画任何官方侧栏内容，也不碰官方 DOM。代价是这几秒左侧是一条与背景同色的空白带（不是灰块）。

### 先遣期只挂顶条（v3.1）

原先 `mountPagersEarly()` 把两条都塞进复刻壳的 `barHost`：

```js
host.insertBefore(page.bars[0].bar, host.firstChild);  // 顶条插最前
host.appendChild(page.bars[1].bar);                     // 底条追加末尾
```

`barHost` 里只有这两条元素，「追加到末尾」就等于紧贴顶条下方——实测 t=199ms 时两条分别在 **y=67 / y=107**（只差 40px），看起来就是「两排分页按钮挤在顶部」。

**做法**：先遣期**只挂顶条**（底条是「翻到底的快捷入口」，列表没铺开时没有意义）；`mountPagers()` 迁到正式兄弟位置时才补挂底条，那时它才落在真正的页面底部。`updatePagers()` 的显示条件相应加一条「底条必须已连接」。实测换装后两条分别是 y=125 / y=12411（顶、底各一）。

### 让官方渲染在复刻期「停住」（v3.2）

**问题**：复刻期官方那份列表只是 `opacity:0`，**布局照常**——导航后 0.3 秒起主线程就被官方物化 5000+ 行占满。实测复刻期累计长任务 **2095ms、单次最长 537ms**；复刻页只有 175 行，却和官方的全量渲染抢同一个线程，所以那几秒滚起来会顿。

**为什么不能直接藏掉官方容器**（都试过，都不能用）：

| 手段 | 结果 |
|---|---|
| `display:none` | 容器不再生成盒子 → `IntersectionObserver` 永远判「不相交」→ 官方分片渲染停摆，换装时一片空白 |
| `visibility:hidden` | 同上（IO 判不可见）。曾实测 90 秒零渲染零报错，极易误判成「抖动」 |
| **`content-visibility: hidden`** ✅ | **子树整体跳过布局与绘制，但元素自身仍在渲染树里、仍生成盒子** → IO 照常判相交，官方渲染推进不受阻，而几千行的布局开销被整块跳过 |

**唤醒时机**（这一步连错两次，记下来）：

| 唤醒条件 | 复刻期 | 单次最长任务 | 问题 |
|---|---|---|---|
| 等 `page.on` | 8.9s ❌ | 134ms | `page.on` 依赖补丁测量，测量又依赖官方渲染出的行 → **循环等待**，一直撑到 6s 超时才放权 |
| 官方物化到 200 行 | 1.7s | 312ms ⚠️ | 阈值附近正是官方物化**最重**的一段，一放权大长任务立刻回来 |
| **自己的复刻页画好（`rp.rows > 0`）** ✅ | **1.3s** | **240ms** | 复刻页 ~0.5s 就画好，按住它零代价；官方最重的那一段被完整跳过 |

结论：**唤醒要看「我自己就绪没有」，不要看对方的进度**——因为对方的进度恰恰是被你按住的那个东西。

**实测对比**（同一台机器、同数据、连跑三轮取稳定值）：

| 指标 | v3.1（只 opacity） | v3.2（+ 按住官方） |
|---|---|---|
| 复刻期首行可读 | ~420ms | ~420ms |
| 复刻期总时长 | 3.0s | **1.3–2.0s** |
| 单次最长长任务 | **537ms** | **240ms**（-55%） |
| 复刻期累计长任务 | 2095ms | **1507ms**（-28%） |

⚠️ 剩下那个 240ms 出现在**换装之后**（官方放权后自己跑完），原版也存在、只是被 537ms 盖住了。要消掉它得改官方渲染本身，不在本补丁范围内。

**另外修了一个滚动容器高度 bug**：复刻壳的滚动容器原先只写了 `overflow:auto` 而没给 `height`，于是它被内容撑开、变成「整页滚动」——复刻期能滚出 5 万像素的伪长页（实测 `scrollHeight` 795 → 修后 5313，与一页 175 行的高度吻合）。补上 `height:100%` 后复刻期的滚动行为与官方一致。

## 安装 / 重打 / 停用

```powershell
# 打 / 重打补丁（幂等，官方升级后重跑即可跟进）
.\OneTab-Performance-Patch\apply_patch.ps1 -TargetDir "...\OneTab-patched-unpacked"
# 停用（恢复官方原状，做对照实验用）
.\OneTab-Performance-Patch\apply_patch.ps1 -TargetDir "...\OneTab-patched-unpacked" -Disable
```

之后在 `edge://extensions` 里对魔改版点「重新加载」。

## 已知边界

1. **打开列表页仍有官方固有的一次性渲染成本**（~0.7s 的长任务来自官方同步建 5.6 万个节点，补丁无法替它建）。补丁自身追加的成本是一次全量测量（关掉 CSS 兜底后把每行真实高度量一遍），已通过单遍读数 + 整容器隐藏压到最低。彻底消灭它的路径是「按需物化」：首次只精测当前页，其余行用 content-visibility 的估算高度顶着、翻到哪页精测哪页——但官方标题可换行（`word-break: break-word`），行高不统一，估高会引入位置误差，需要更细的设计，留作 v3。
2. **窗口尺寸剧烈变化 / 字体加载完成**会触发一次全量重测（罕见路径，秒级）。
3. 搜索结果分页依赖官方行高为 0 的语义（官方藏的行量出来是 0 高度），这与官方实现一致，官方若改用别的隐藏方式需要跟进。
